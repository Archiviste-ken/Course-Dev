Mutable vs Immutable in Redux — Beginner Notes
These notes explain one of the most important ideas in Redux. Take it slow. Each part builds on the one before it.

1. What do "mutable" and "immutable" mean?
These are just fancy words for a simple idea:

Mutable = "can be changed." You take the original thing and edit it directly.
Immutable = "cannot be changed." You leave the original alone and make a fresh copy with your change inside the copy.

A real-life way to picture it:
Imagine you have a document.

Mutable way: you open the document and type over the old words. Same document, new content. The old version is gone forever.
Immutable way: you click "Make a copy," then edit the copy. Now you have two documents — the untouched original, and a new one with the change.

That's the whole idea. In Redux, we always work the immutable way: never edit the original, always make a new copy.

2. The hidden idea: "reference"
Before Redux makes sense, you need this one concept. It's small but important.
When you make an object or array in JavaScript, the variable does not hold the object itself. It holds a pointer to where the object lives in memory. This pointer is called a reference.
Think of a variable as a sticky note with an arrow pointing at a box. The box is the real object. The sticky note just points to it.
javascriptconst a = { count: 0 };
Here, a is a sticky note pointing at a box that contains { count: 0 }.
Now watch what happens when we copy the sticky note:
javascriptconst a = { count: 0 };
const b = a;            // copy the sticky note, NOT the box
Both a and b are arrows pointing at the same box. There is still only one box. So if you change the box through one note, the other note sees the change too:
javascriptb.count = 5;
console.log(a.count);  // 5  ← changed, because a and b point to the SAME box
To get a real copy (a brand-new box), you have to build a new object yourself:
javascriptconst a = { count: 0 };
const b = { ...a };    // the "..." makes a NEW box with the same stuff inside
b.count = 5;
console.log(a.count);  // 0  ← a is untouched, because b is a different box
That little ... is called the spread operator. You'll use it constantly. It means "copy everything from the old object into a new one."
Quick test you'll see everywhere — the === check:
JavaScript can ask "are these two sticky notes pointing at the exact same box?" using ===:
javascriptconst a = { count: 0 };

const b = a;            // same box
a === b;                // true  → same box

const c = { ...a };     // new box
a === c;                // false → different box (even though contents look identical!)
Notice: a and c have the same contents, but === still says false, because they are two different boxes. === checks the box, not the contents. Remember this — it is the key to why Redux behaves the way it does.

3. Why does Redux care so much about this?
Here is the reason behind everything.
Redux holds your app's data (the "state"). When something changes, Redux needs to figure out: "Did the state actually change? If yes, I'll update the screen."
You might expect Redux to carefully look inside the state and compare every single value. It does not do that — that would be slow. Instead, Redux does the cheap, fast check:

"Is the new state a different box than the old one?" (using ===)


Different box → "Something changed!" → updates the screen.
Same box → "Nothing changed." → does not update the screen.

Now you can see the trap. If you edit the state directly (mutable way), the box stays the same. So Redux compares old and new, sees the same box, and thinks nothing happened — even though you changed the contents inside.
javascriptconst oldState = { count: 0 };

// MUTABLE (wrong) — editing the same box
const newState = oldState;
newState.count = 1;
oldState === newState;     // true  → Redux thinks "no change", screen does NOT update 😞

// IMMUTABLE (right) — a brand-new box
const newState2 = { ...oldState, count: 1 };
oldState === newState2;    // false → Redux thinks "changed!", screen updates 😀
The scary part: mutating does not show an error message in plain Redux. Your code runs fine, nothing crashes — the screen just silently refuses to update. This is one of the most confusing bugs for beginners, because everything looks correct. That's why the rule below matters so much.

4. The Golden Rule of Redux

Never change the existing state. Always return a brand-new copy with your changes inside it.

If you remember nothing else, remember that sentence.

5. Updating objects the immutable way
The pattern is always: spread the old object into a new one, then set the field you want to change.
javascriptconst state = { name: 'Alice', age: 25 };

// change age, keep everything else
const newState = { ...state, age: 26 };
// result: { name: 'Alice', age: 26 }
How to read { ...state, age: 26 }:

...state → "copy everything from the old object into this new one."
age: 26 → "but set age to 26." (If a key already exists, the later value wins.)

You can add a new field the same way:
javascriptconst newState = { ...state, email: 'alice@mail.com' };
// result: { name: 'Alice', age: 25, email: 'alice@mail.com' }

6. Updating arrays the immutable way
Arrays are trickier because some array methods secretly change the original array. You must avoid those in Redux.
❌ Methods that MUTATE (avoid these — they edit the original)
push, pop, shift, unshift, splice, sort, reverse
✅ Methods that are SAFE (they return a new array, leaving the original alone)
map, filter, concat, slice, and the spread [...]
Here are the four things you'll do most often, all done the safe way:
javascriptconst items = [1, 2, 3];

// ADD an item
const added = [...items, 4];                 // [1, 2, 3, 4]

// REMOVE an item (keep everything that is NOT 2)
const removed = items.filter(x => x !== 2);  // [1, 3]

// UPDATE an item (turn 2 into 20, leave the rest)
const updated = items.map(x => (x === 2 ? 20 : x));  // [1, 20, 3]

// SORT safely (make a copy first, then sort the copy)
const sorted = [...items].sort();            // original 'items' stays untouched
That last one is a common trap: items.sort() would sort the original array in place (mutation!). By copying first with [...items], you sort the copy instead and the original is safe.

7. Nested objects (the part everyone finds annoying)
If your data has objects inside objects, you must make a new copy at every level you touch — not just the top.
javascriptconst state = {
  user: {
    name: 'Alice',
    address: { city: 'NYC' }
  }
};
Say you want to change the city to 'LA'. You have to spread at all three levels:
javascriptconst newState = {
  ...state,                       // new top-level box
  user: {
    ...state.user,                // new user box
    address: {
      ...state.user.address,      // new address box
      city: 'LA'                  // the actual change
    }
  }
};
Why so much work? Because each level is its own box. If you only copied the top and reused the inner user box, you'd accidentally be sharing (and mutating) the original's inner data. So you rebuild every box on the path down to the thing you're changing.
Yes — this is verbose and easy to get wrong. That pain is exactly why the modern tool below exists.

8. The modern way: Redux Toolkit (what people actually use today)
Writing all those spreads by hand is tiring. So the official, recommended version of Redux — called Redux Toolkit (often written RTK) — solves it for you.
RTK includes a helper called createSlice. Behind the scenes, createSlice uses a library named Immer. Immer does something almost magical: it lets you write code that looks like mutation, but it secretly converts it into a correct immutable copy for you.
javascriptimport { createSlice } from '@reduxjs/toolkit';

const counterSlice = createSlice({
  name: 'counter',
  initialState: { count: 0, items: [] },
  reducers: {
    increment: (state) => {
      state.count += 1;                 // looks like mutation — but Immer makes it safe
    },
    addItem: (state, action) => {
      state.items.push(action.payload); // even push is OK here!
    }
  }
});
Wait — didn't we just spend this whole lesson saying never do state.count += 1 and never use push? Yes. The trick is that the state inside an RTK reducer is not the real state — it's a special temporary "draft" that Immer watches. You scribble your changes on the draft, and Immer quietly produces a proper new copy from it. So the Golden Rule is never actually broken; Immer just does the copying for you.
Three things to keep straight about Immer (important):

It only works inside RTK reducers (createSlice or createReducer). Anywhere else — inside your components, your selectors, or a plain hand-written reducer — there is no Immer, so the old rule still applies: copy manually with spread.
Don't mix the two styles in one reducer. In a single reducer function, either change the draft (and return nothing), or build and return a new object yourself — never do both in the same function.
RTK actually warns you if you mutate by accident (outside the draft, in development mode). This is a bonus safety net that plain Redux does not have. So with RTK, the silent-bug problem from Section 3 is much less likely to bite you.

10. Common beginner mistakes to watch for

Editing state directly and wondering why the screen won't update. (state.count = 5) → silent bug. Use a copy.
Using push / splice / sort on state arrays. They mutate. Use [...], filter, map, or copy-then-sort.
Only copying the top level of a nested object. You must copy every level down to the value you're changing.
Forgetting Immer doesn't exist outside RTK reducers. In a component, state.push(x) is still wrong.
Mixing draft-mutation and return in the same RTK reducer. Pick one style per reducer.


One-line summary
In Redux you never change the existing state — you replace it with a fresh copy. That's because Redux checks whether the state is a new box (not whether the contents differ), so editing the old box silently does nothing. Plain Redux: copy by hand with .... Redux Toolkit: write mutation-looking code and let Immer copy for you.
